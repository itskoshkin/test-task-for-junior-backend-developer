# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

## Предположения и решения

Здесь зафиксированы решения по реализации фичи

- **Шаблон + инстансы**  
    Периодичность живёт в отдельной сущности `task_templates`. Конкретные задачи на дату (`tasks`) — её инстансы. Разовая задача — это `tasks` с `template_id = NULL`. Такой подход позволяет иметь свой статус у каждого дня серии, редактировать отдельные инстансы и единообразно работать с разовыми и периодическими задачами
- **Дискриминируемый тип правила**  
    Фиксированный набор типов: `daily`, `monthly`, `specific_dates`, `weekday_parity` (из ТЗ) + `last_day_of_month` как расширение под частый use-кейс (месячная отчётность, инвентаризация). В БД будет `rule_type` `TEXT` + `rule_params` `JSONB`
- **Ленивая материализация**  
    Строка в `tasks` создаётся только при первой мутации конкретного дня (смена статуса). До этого инстансы виртуальные и считаются на лету при запросе окна. Это избавляет от фонового воркера и бесконечно растущей таблицы
- **Календарный день, а не момент времени**  
    Правила и `due_date` — тип `DATE` без времени. Часовой пояс не участвует в бизнес-логике: клиент присылает `YYYY-MM-DD` в своей интерпретации, сервер оперирует календарными днями. Это делает сервис TZ-agnostic: при появлении пользователей в разных часовых поясах ничего менять не надо. В UTC хранятся только системные
  `created_at`/`updated_at`
- **Чётность** считается по номеру дня месяца 
- **`end_date` шаблона** инклюзивный, может быть `NULL` (бесконечное правило)
- **Удаление шаблона** каскадно удаляет материализованные инстансы (`ON DELETE CASCADE`)
- **Окно чтения обязательно**  
    `GET /api/v1/tasks` требует параметры `from`/`to`, максимум 366 дней за запрос (иначе легко выстрелить себе в ногу при шаблоне без `end_date`)
