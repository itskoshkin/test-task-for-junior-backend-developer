# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файлы из `migrations/` монтируются в `docker-entrypoint-initdb.d` и применяются только при инициализации пустого data volume.

## Тесты

Юнит-тесты (без внешних зависимостей):

```bash
go test ./...
```

E2E через поднятый docker-compose (сервис должен быть запущен):

```bash
go test -tags=e2e ./test/e2e/...
```

E2E-тест создаёт шаблон, читает окно, переключает статус одной даты и проверяет ленивую материализацию через живую БД. По умолчанию стучится в `http://localhost:8080`, переопределяется переменной `API_URL`.

## API

Базовый префикс:

```text
/api/v1
```

### Разовые задачи

- `POST   /tasks` — создать разовую задачу (`template_id` не указывается, `due_date` опционален)
- `GET    /tasks/{id}` — получить задачу по ID
- `PUT    /tasks/{id}` — обновить задачу (`due_date`: omit — оставить как есть, `null` — очистить, строка даты — заменить)
- `DELETE /tasks/{id}` — удалить задачу
- `GET    /tasks` — список задач
    - без параметров — все материализованные задачи (пагинация через `limit`/`offset`)
    - с `from`/`to` — материализованные и виртуальные вхождения в окне (оба параметра обязательны вместе, максимум 366 дней)
- `PATCH  /tasks/status` — переключить статус вхождения. Если передать `id` — апдейтит материализованную задачу. Если передать `template_id` + `due_date` — материализует виртуальное вхождение (идемпотентно: повторный вызов обновит существующую строку, а не создаст дубль)

### Шаблоны периодических задач

- `POST   /task-templates` — создать шаблон с правилом
- `GET    /task-templates/{id}` — получить шаблон
- `PUT    /task-templates/{id}` — обновить шаблон (правило, период, заголовок)
- `DELETE /task-templates/{id}` — удалить шаблон (каскадно удаляет материализованные инстансы)
- `GET    /task-templates` — список шаблонов с пагинацией

## Примеры (curl)

Создать шаблон «каждый день начиная с 2026-04-18»:

```bash
curl -X POST http://localhost:8080/api/v1/task-templates \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Обзвон пациентов",
    "rule": {"type": "daily", "params": {"every_n": 1}},
    "start_date": "2026-04-18"
  }'
```

Другие типы правил в поле `rule`:

```jsonc
// каждые 3 дня
{"type": "daily", "params": {"every_n": 3}}

// 1-го и 15-го числа каждого месяца
{"type": "monthly", "params": {"days_of_month": [1, 15]}}

// только на конкретные даты
{"type": "specific_dates", "params": {"dates": ["2026-04-20", "2026-05-01"]}}

// по чётным числам месяца (2, 4, 6, ...)
{"type": "monthday_parity", "params": {"parity": "even"}}

// последний день месяца (28/29/30/31 в зависимости от месяца и високосного года)
{"type": "last_day_of_month", "params": {}}
```

Создать разовую задачу без срока:

```bash
curl -X POST http://localhost:8080/api/v1/tasks \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Разобрать входящие"
  }'
```

Создать разовую задачу со сроком:

```bash
curl -X POST http://localhost:8080/api/v1/tasks \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Подготовить выписку",
    "due_date": "2026-04-20"
  }'
```

Прочитать окно — получаем и материализованные задачи, и виртуальные вхождения шаблонов:

```bash
curl 'http://localhost:8080/api/v1/tasks?from=2026-04-18&to=2026-04-25'
```

Ответ содержит массив задач. Виртуальные вхождения отличаются флагом:

```jsonc
{
  "id": 0,                  // 0 у виртуальных, реальный ID — у материализованных
  "template_id": 42,
  "title": "Обзвон пациентов",
  "status": "new",
  "due_date": "2026-04-19",
  "virtual": true           // true — сгенерировано на лету, строки в БД ещё нет
}
```

Переключить статус виртуального вхождения (материализует строку в БД):

```bash
curl -X PATCH http://localhost:8080/api/v1/tasks/status \
  -H 'Content-Type: application/json' \
  -d '{
    "template_id": 42,
    "due_date": "2026-04-19",
    "status": "done"
  }'
```

Переключить статус уже материализованной задачи (или разовой) — по ID:

```bash
curl -X PATCH http://localhost:8080/api/v1/tasks/status \
  -H 'Content-Type: application/json' \
  -d '{"id": 123, "status": "in_progress"}'
```

Обновить разовую задачу и очистить срок:

```bash
curl -X PUT http://localhost:8080/api/v1/tasks/123 \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Подготовить выписку",
    "status": "in_progress",
    "due_date": null
  }'
```

## Предположения и решения

Т.к. ТЗ даёт свободу в проектировании, ниже зафиксированы принятые решения и их обоснование

- **Шаблон + инстансы**  
    Периодичность живёт в отдельной сущности `task_templates`. Конкретные задачи на дату (`tasks`) — её инстансы. Разовая задача — это `tasks` с `template_id = NULL`. Такой подход даёт свой статус у каждого дня серии, позволяет редактировать отдельные инстансы и единообразно работать с разовыми и периодическими задачами.
- **`due_date` опционален для разовых задач**  
    В исходной модели у `Task` срока не было, поэтому делать `due_date` обязательным для `POST /tasks` означало бы сломать обратную совместимость и убрать сценарий «задача без срока». В результате колонка `due_date` nullable: разовые задачи могут жить без даты, а шаблонные инстансы всегда имеют `due_date` — это инвариант recurrence-фичи.
- **Дискриминируемый тип правила**  
    Фиксированный набор типов: `daily`, `monthly`, `specific_dates`, `monthday_parity` (из ТЗ) + `last_day_of_month` как расширение под частый use-кейс (месячная отчётность, инвентаризация). В БД — `rule_type TEXT` + `rule_params JSONB`. В JSON API — теговый union с полем `type`.
- **Ленивая материализация**  
    Строка в `tasks` создаётся только при первой мутации конкретного дня (смена статуса). До этого инстансы виртуальные и считаются на лету при запросе окна. Это избавляет от фонового воркера и бесконечно растущей таблицы, но сохраняет возможность иметь отдельный статус/правки у каждого дня.
- **Идемпотентная материализация**  
    `PATCH /tasks/status` по `template_id`+`due_date` использует `INSERT ... ON CONFLICT` по частичному уникальному индексу `(template_id, due_date) WHERE template_id IS NOT NULL`. Индекс частичный, чтобы разовые задачи (`template_id IS NULL`) не участвовали в дедупликации.
- **Календарный день, а не момент времени**  
    Правила и `due_date` — тип `DATE` без времени. Часовой пояс не участвует в бизнес-логике: клиент присылает `YYYY-MM-DD` в своей интерпретации, сервер оперирует календарными днями. Это делает сервис TZ-agnostic: при появлении пользователей в разных часовых поясах ничего менять не надо. В UTC хранятся только системные `created_at`/`updated_at`.
- **Чётность** считается по номеру дня месяца, не дня недели (это явное требование ТЗ: «чётные/нечётные дни месяца»). 31-е число попадает под «нечётные».
- **`monthly` с днями 29/30 в месяцах без них** — пропускается, не сдвигается. Для «последнего дня месяца» есть отдельный тип `last_day_of_month`.
- **`end_date` шаблона** инклюзивный, может быть `NULL` (бесконечное правило).
- **Удаление шаблона** каскадно удаляет материализованные инстансы (`ON DELETE CASCADE`). Альтернатива — soft-delete шаблона — отложена: в ТЗ нет требования сохранять историю удалённых серий.
- **Окно чтения обязательно**  
    `GET /tasks` c периодическими инстансами требует `from`/`to`, максимум 366 дней за запрос. Иначе при шаблоне без `end_date` ответ может раздуться произвольно. Без `from`/`to` эндпоинт возвращает только материализованные задачи — это отдельный режим для админки/списка.
- **Пагинация**  
    `limit` (по умолчанию 20, максимум 100) и `offset` работают в обоих режимах. В оконном режиме пагинация применяется **после** слияния материализованных и виртуальных вхождений — иначе пришлось бы либо материализовать всё окно ради корректной пагинации, либо нарушать порядок.

- **Почему не RRULE (iCal)**  
    Можно было взять [RFC 5545 RRULE](https://datatracker.ietf.org/doc/html/rfc5545#section-3.3.10) и хранить правила строкой вида `FREQ=MONTHLY;BYMONTHDAY=1,15`. Это индустриальный стандарт, и для него есть готовые парсеры.  
    В этом проекте выбрал кастомный дискриминируемый union по следующим причинам:
    1. **Набор правил из ТЗ — узкое подмножество RRULE плюс специфические типы.** «Чётные/нечётные дни месяца» в RRULE напрямую не выражаются (приходится перечислять `BYMONTHDAY=2,4,6,...,30` — работает, но это не то же самое, что «правило чётности»). Валидировать такое приходится руками, и UI-слой, редактирующий правило, всё равно оперирует доменными типами, а не строкой RRULE.
    2. **Много ненужной выразительности.** RRULE описывает `FREQ=SECONDLY`, `BYSECOND`, `BYHOUR`, `BYSETPOS`, `BYYEARDAY`, сложные комбинации — всё это пришлось бы либо валидировать и запрещать, либо закладывать поведение на корнер-кейсы, которые продукту не нужны.
    3. **UX формы создания задачи.** Концептуальная пикча из ТЗ показывает радиогруппу с четырьмя явными вариантами. Union с дискриминатором `type` маппится на неё один-в-один: тип = выбранный radio, `params` = поля формы. RRULE заставил бы городить сериализацию/десериализацию между доменной моделью формы и строкой.
    4. **Простая валидация и тесты.** Каждый тип — отдельная структура со своими инвариантами (`every_n >= 1`, `days_of_month ⊂ [1..30]`, непустой `dates` и т.д.). Проверяется Go-кодом без диалекта RRULE.  
    Если в будущем потребуется интероп с внешними календарями (iCal-экспорт, импорт из Google Calendar) — слой конвертации «домен → RRULE» добавится поверх, без перелопачивания хранилища.
